## Goal (the user's decision, 2026-10-15)

One mod, built in this repo, that merges the "assessor" idea with the approved P7 (per-step
effort governor). The mods session (`claude-code-mods-artefacto`) dropped P7 from its plan and
will not touch `turn.step` effort; its Jira mod uses `prompt.submit` and UI only.

The user's words (translated): the mod categorizes the task's difficulty and gives the session
a **recommendation**: which effort it needs, from low to max. It is only a recommendation; the
**final decision belongs to Opus** (the main model). Same for the advisor: first, advisor yes or
no; second, if yes, at what effort, low to max. The advisor must **always be above the main
session**: if the main effort is medium, the advisor's is high.

Also decided the same day: skills carry no `effort:` (removed from security-audit and
pr-review); the advisor stays on by default.

## Verified facts that constrain the design

### Effort

- Hooks cannot change effort. Skill/agent frontmatter `effort` applies while that skill or
  agent is active and lasts the rest of the turn (`docs/model-uplift-playbook.md`). `ultrathink`
  works only when the user types it and does not change API effort. `/effort` + `s` = session
  only; Enter persists into the generated settings (sync trap, see memory `sync-scripts`).
- In user settings only `modelSettings["claude-opus-5-5"].effortLevel` applies to Opus 5.5
  (`settings.global.json` pins `medium`). Top-level `effortLevel` is ignored for Opus 5.5.
- The main model cannot change its own effort. Only a mod can, per request.

### Mod API (answers from the mods session, round 1)

1. `turn.step` fires right before each request; `effort` is "the session's setting or the
   model's default; rewritable". A hook's `next({...e, effort})` is the last write, so it should
   win over frontmatter. Covers subagent steps through `e.agentId`. The account runs the
   sec-default guard; `turn.*` stays allowed. [d.ts verified: `index.d.ts:4450-4460,
   13428-13457`; frontmatter precedence inferred, **not tested live**]
2. `$.model.classify` = one completion over `$.model.complete` with a fixed classifier prompt,
   on `options.model`, default "the engine's small fast model" (`index.d.ts:1397-1403,
   2646-2662`). **Latency unmeasured.** Nearest measure: the router's headless Haiku call,
   2.3-2.5 s wall, 1.1-1.25 s API, 9.5k cached input tokens.
3. `prompt.submit` context reaches the main model before step 0 (observed). Survival through
   compaction unverified; it is attached to one user message, so re-inject per prompt.
4. The advisor is an API server tool: it appears only after the fact in `turn.step`'s
   `response.serverToolUses`. No `tool.check`/`tool.call`/`tool.describe` chain and no classic
   hook runs for it, so a mod **cannot attach, detach, refuse or rewrite** it through tool hooks;
   instructions are the lever. A mod can count `serverToolUses` named `advisor` to measure
   compliance. [verified: `index.d.ts:13512-13560`]
5. Mods live in `plugins/<name>` of this repo (hud, vista, dock, workboard; `plugins/dock` is
   git-tracked, the rest of `plugins/` is untracked: deletes there are unrecoverable). Types:
   `plugins/hud/.claude-plugin/types/claude-code/index.d.ts`, generated by 2.1.296 (binary is
   2.1.300). Installed copies are cached: version bump + `claude plugin update`. Company-only
   content goes to poneglyph-work, whose addon vetoes hooks, so mods live here.
6. P1 (router in-process as a mod) was rejected: only 5 of 189 measured turns (2.6 %) edited
   anything before the async router note arrived.

### Advisor (code.claude.com/docs/en/advisor and platform advisor-tool docs, fetched 2026-10-15)

- Claude decides when to call it. "There is no setting to cap or force advisor calls; if you
  want Claude to consult more or less often during a task, say so in your instructions."
- **The advisor has no effort parameter.** Tool fields: `type` `advisor_20260301`, `name`,
  `model` (required), `max_uses` (per request, not per conversation; over the cap returns
  `max_uses_exceeded` and the executor continues), `max_tokens` (caps the advisor's thinking
  plus text per call, min 1024), `caching` (`{"type":"ephemeral","ttl":"5m"|"1h"}`). "The
  advisor itself runs without tools and without context management. Its thinking blocks are
  dropped before the result returns."
- So "advisor one level above the main effort" can only be expressed through: the advisor
  **model** (for an Opus 5.5 main: Fable or Opus 5+; an advisor must rank at or above the main
  model), and **`max_tokens`** as a proxy for depth, and only if `turn.step` can rewrite the
  request's tool definition (round 2, Q2). Otherwise it is fixed by `advisorModel`.
- Model choice: `/advisor X` (persists into the generated settings: sync trap), `advisorModel`
  setting, `claude --advisor X` (one session, hidden from `--help`). Off: `/advisor off`;
  `CLAUDE_CODE_DISABLE_ADVISOR_TOOL=1`. Toggling does not invalidate the main prompt cache. The
  advisor's own read is never cached. Subagents inherit the advisor with the same pairing check.
- Usage: top-level `usage` is executor-only; `usage.iterations[]` entries with
  `type: "advisor_message"` carry the advisor's tokens and model. Advisor usage does show in
  `/usage`.

  ≈ 16 % of total spend. In this session it caught 5 real errors in a deliverable and 5 gaps in

- Main sessions ≈ $2,437; subagents ≈ $91.

## Design draft (to confirm with round 2, then present to the user)

1. `prompt.submit`: classify the prompt (trivial / normal / high, or a finer low..max scale)
   with `$.model.classify`; inject a short note: recommended main effort, advisor yes/no and
   its level, and the rule "you decide; call `<tool>` to apply". Re-inject on every prompt.
2. A mod-registered tool (`$.tool.register`, as dock/vista/workboard do) that Opus calls with
   its final choice `{main, advisor}`. Mod state keeps it for the turn.
3. `turn.step`: apply the chosen main effort to every request of the turn (decide: main only,
   or subagents too via `e.agentId`). If round 2 Q2 allows it, set the advisor tool's
   `max_tokens`/`max_uses` from the advisor level; else the advisor part is an instruction only.
4. Fallbacks: classify error or timeout → no note, session effort unchanged. Unknown effort
   value → do not write it.
5. Observability: log per turn: recommended level, chosen level, applied effort, advisor calls
   counted from `serverToolUses`, classify latency. A doctor/compliance row later.
6. Tests: `claude plugin test` plus unit tests of the classifier mapping and the state machine;
   real flow: a trivial and a hard prompt in a live session, read the log.

Open risks: classify latency on every prompt; misclassification raises cost; Opus may ignore
the recommendation (measure follow rate); "max" validity per model; frontmatter precedence.

## Prior art and the cache problem (researched 2026-10-15; decides the design)

**Cache fact, updated the same day (supersedes the first reading).** A *top-level*
`output_config.effort` change still invalidates the cache (thinking-steering-and-cost; prompt-caching
table). But per-message effort keeps it: "On Claude Fable 5.1, Claude Mythos 5.1, Claude Opus 5.5,
Claude Opus 5, Claude Sonnet 5.5, and Claude Haiku 5.5, use a per-message effort change, which keeps
the prompt cache" (platform effort docs, beta `mid-conversation-output-config-2026-07-01`; a
`role:"system"` message with empty content and `output_config.effort`). It applies from the next
`user` turn with new input; a `user` turn holding only `tool_result` blocks does not count, so a
change mid tool loop waits for the next prompt.

Claude Code uses it: "On Opus 5.5, Sonnet 5.5, Haiku 5.5, and Fable 5.1 with an API key or a Claude
subscription, changing effort keeps the cache, and Claude Code applies the new level without
asking" (code.claude.com/docs/en/prompt-caching §Changing effort level; not on Bedrock, Vertex, the
Claude apps gateway, `CLAUDE_CODE_DISABLE_EXPERIMENTAL_BETAS` or HIPAA). Fable 5.1 got it in
v2.1.260. The 2.1.300 binary carries `k("per_message_effort","per-turn-control-2026-07-01")`.
Issue anthropics/claude-code#92444 (2026-09-06, open) measured full rewrites on Opus 5 and partial
on Sonnet 5 at that time; it predates the doc change.

Local evidence (`scratchpad/effort_cache.py` over `~/.claude/projects/*/*.jsonl`): the turn after
`/effort high` on Opus 5.5 read 124,400 cached / wrote 1,345 (2026-09-24, prev turn read 122,520)
and read 83,783 / wrote 3,440 (2026-10-14, 34 min gap, inside the 1 h TTL). n=2, and the previous
level is not logged, so "it changed" is probable, not proven.

**Still unknown:** whether a mod's `turn.step` effort rewrite goes through the per-message path or
the top-level field. The d.ts (13436-13457) does not say. **Measure first**: a probe mod rewrites
effort on `index 0` of one prompt; read `cache_read_input_tokens` on that request and the next.

Other facts from the same page: thinking is adaptive per request at every level ("the model
evaluates each request and determines whether to think and how much"); effort is "soft
guidance". Per-message steering is documented for harnesses: "An agent harness, for example, can
append the encouraging phrase on planning steps and the discouraging phrase on routine
confirmations, without touching the system prompt or changing any request parameters." Phrases:
"Please think hard before responding." / "Answer directly without deliberating." (the
discouraging one is unreliable on Haiku 5.5 and Sonnet 5.5).

Prior art (Haiku research agent, primary URLs; spot-verified only the Claude docs above):
- Model routers per prompt: RouteLLM (arXiv 2406.18665: >2x cost cut on MT-Bench, only 1.14x on
  MMLU; Arena-trained routers near random on MMLU/GSM8K), Hybrid LLM (arXiv 2404.14618: up to 40 %
  fewer large-model calls), FrugalGPT cascades, Cursor Router ("A machine-learning classifier
  routes each Auto request across a pool of models"). They pick a **model**, not effort.
- No primary source found where a classifier sets **effort** per prompt, or shows that a
  prompt-only recommendation beats letting the model adapt. Vendors (Anthropic, OpenAI) set
  effort per workload and let the model adapt inside it. Codex `model_reasoning_effort` and
  Claude Code effort are static; opusplan switches by mode, not by prompt.
- Advisor: Anthropic keeps the decision with the executor ("The executor model decides when to
  invoke it"); the gauge-as-instruction matches that.
- Weaknesses: difficulty from the prompt alone is noisy (no codebase seen yet); router
  confounders (arXiv 2501.01818) can push spend up.

**Design consequence:** the advisor gauge (instruction) is sound and cheap. Effort per prompt is
viable on Opus 5.5 if the probe shows `turn.step` keeps the cache: rewrite only on `index 0` (later
steps of the turn are tool-result-only and would wait anyway) and keep the steering text as the
fallback when the probe shows a cache loss. On Fable 5.1 a top-level change also "steers the model
less reliably", another reason to want the per-message path.

### Consequence for the user's mapping

- Main effort low..max: feasible. The mod recommends, Opus chooses through the mod's tool, and
  `turn.step` applies it from the next request (the current request already went out).
- Advisor yes/no: instruction only ("do not call the advisor" / "call it before the plan and
  before done"); compliance measurable by counting `serverToolUses` named `advisor`.
- **Advisor effort "one level above the main": not implementable by a mod.** The advisor tool has
  no effort parameter, and the mod cannot touch the tool definition. The only real lever is the
  advisor model (`advisorModel`, e.g. Fable above an Opus main), set by the user, not per turn.
  Tell the user before designing; offer: advisor model fixed at the strongest allowed (Opus or
  Fable), and the mod varies only whether and when Opus consults it.

### Advisor barometer (user's refinement, 2026-10-15, after learning the above)

The mod cannot switch the advisor off, so it **recommends** how much to use it, the same way the
router recommends skills; Opus decides. One gauge per prompt, in the same note as the effort
recommendation:

| Level | Note to Opus (wording to tune) | Typical task |
|---|---|---|
| 0 avoid | Better not to call the advisor on this task | Trivial: a question, a read, a one-line edit |
| 1 last resort | Call it only if you are stuck or about to take a risky, hard-to-undo step | Normal, well-scoped work |
| 2 some | Call it once before declaring done | Normal multi-step work |
| 3 a lot | Call it before committing to a plan, when stuck, and before declaring done | High blast radius, design, security |

Facts that shape it:
- The host's own Advisor Tool system text tells the model to call the advisor before substantive
  work and before done. The gauge competes with that text, so levels 0-1 may be followed less.
  Measure: count `serverToolUses` named `advisor` per turn against the recommended level; report
  the follow rate per level before trusting it.
- The note goes in `prompt.submit` on every prompt (it does not survive compaction).
### Two axes, not one (user's refinement, same day)

Difficulty and uncertainty are classified separately:
- **Difficulty → main effort** (low..max): how much reasoning every step needs.
- **Uncertainty → advisor gauge** (0..3): how likely the task hits a point where a second
  opinion pays (unclear cause, ambiguous spec, risky or irreversible step).

The case that motivates it: an easy task with some doubt runs at **medium** effort, with gauge
**1 "call it when the doubt shows up"**, instead of raising the whole session's effort. The
advisor then covers the uncertain moment, and the routine steps stay cheap. Evidence that the
pattern works: the platform advisor-tool docs say "pairing a Sonnet executor at medium effort
with an Opus advisor achieves intelligence comparable to Sonnet at default effort"
(executor-level effort, not ours; there is no published data for Opus + Opus).

| | Low uncertainty | Some uncertainty | High uncertainty |
|---|---|---|---|
| Easy | low · 0 | medium · 1 | medium · 2 |
| Normal | medium · 1 | medium · 2 | high · 2 |
| Hard | high · 2 | high · 3 | xhigh/max · 3 |

Starting values, to tune with the follow-rate and cost logs. For each level, the note names the
trigger, not only the amount ("call it when the cause of a failure is unclear", "before an
irreversible step"). Two `classify` calls run in parallel (one per axis, few labels each), or
one with combined labels. Measure which is more accurate and faster before choosing.
